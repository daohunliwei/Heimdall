# 全仓库技术栈迁移与中文化规格说明

## 背景与动机
当前仓库采用 Python 后端与 Next.js 前端的双栈实现，同时存在多语种文档、界面文案与注释，且 Python 代码直接位于主目录结构中，不利于后续将仓库主干收敛为 C# 与 Next.js 双技术栈。需要先将现有 Python 代码集中到独立子目录，再逐步完成 C# 后端替换、中文化收敛与 Agent 协作规范建设，以降低维护复杂度并明确主目录边界。

## 变更内容
- 在迁移开始阶段，先将现有 Python 后端及相关 Python 测试、脚本、配置集中迁移到独立子目录，避免继续污染主目录。
- 将现有 Python 后端逐步迁移为基于 ASP.NET Core 且运行时固定为 `.NET 10` 的 C# 后端服务，并保持现有核心业务能力可被前端继续调用。
- 保留并延续现有 `src/` 下的 Next.js 前端，改造其接口接入层以适配新的 C# 后端。
- 对仓库根目录进行结构治理，目标是在迁移完成后主目录仅保留 C# 后端、Next.js 前端及必要的仓库级配置。
- 清理仓库内的多语种文档、界面文案与代码注释，仅保留中文版本与中文注释。
- 新增完整的 `Agents.md`，定义仓库结构、职责边界、开发流程、常见任务入口、验证方式与修改约束。
- 调整构建、启动、测试与 CI 配置，使其匹配新的前后端技术栈。
- **破坏性变更**：现有 Python 相关目录、脚本与测试位置会在迁移初期发生目录调整。
- **破坏性变更**：Python 后端启动方式、依赖管理、测试入口与部署方式将发生变化。
- **破坏性变更**：多语种文档与国际化资源将被精简为中文单语版本。

## 影响范围
- Affected specs: 后端服务架构、仓库目录治理、前端接口契约、仓库文档规范、国际化策略、开发协作规范、CI/CD 流程
- Affected code: `api/`、`tests/`、`test/`、`src/`、`README*`、`package.json`、`Dockerfile`、`docker-compose.yml`、`.github/workflows/*`、新增 `Agents.md`、Python 收拢目录与 C# 后端目录

## 新增要求
### 要求：Python 代码先收拢到独立子目录
系统 SHALL 在迁移开始时先将现有 Python 后端、Python 测试与相关脚本整体收拢到统一的独立子目录中，使仓库主目录后续只承载 C# 与 Next.js 的主逻辑。

#### 场景：迁移初期完成目录收拢
- **当** 迁移工作正式开始
- **则** 现有 Python 代码、测试与配套脚本被集中移动到约定的独立子目录
- **则** 仓库主目录不再继续新增分散的 Python 业务逻辑
- **则** 后续 C# 后端与 Next.js 前端可在更清晰的主目录结构中演进

### 要求：C# 后端替换 Python 后端
系统 SHALL 提供一个基于 ASP.NET Core 且运行时固定为 `.NET 10` 的 C# 后端，用于替换当前 `api/` 目录下的 Python 服务，并承接现有仓库分析、文档生成、流式问答、配置读取等核心能力。

#### 场景：前端通过新后端成功生成 Wiki
- **当** 用户在 Next.js 前端提交仓库地址并触发生成
- **则** 前端调用 C# 后端公开的 HTTP 或流式接口
- **则** 后端完成仓库处理、文档生成与结果返回
- **则** 前端无需依赖 Python 运行时即可完成主流程

### 要求：Next.js 前端延续并完成后端适配
系统 SHALL 保留现有 Next.js 前端作为唯一 Web 前端，并将其所有后端调用改造为对接新的 C# 接口契约。

#### 场景：现有页面完成接口切换
- **当** 用户访问首页、Wiki 页面、Ask 或 DeepResearch 相关页面
- **则** 页面仍由 Next.js 提供
- **则** 所有请求均通过新的 C# 后端地址与协议完成
- **则** 原有前端交互行为与主要用户路径保持可用

### 要求：仓库文档与注释仅保留中文
系统 SHALL 将仓库内对外文档、开发文档、注释与默认界面文案统一为中文，不再维护其他语种版本。

#### 场景：开发者查看仓库文档
- **当** 开发者打开根目录 README、子模块说明、部署说明或关键代码注释
- **则** 内容仅提供中文版本
- **则** 仓库中不存在继续维护的多语种 README 与多语种消息资源

### 要求：提供完整的 Agents.md
系统 SHALL 在仓库根目录提供完整的 `Agents.md`，用于指导后续 Agent 或人工开发者进行修改、排障与验证。

#### 场景：Agent 根据文档执行定向修改
- **当** 后续维护者或 Agent 阅读 `Agents.md`
- **则** 可以了解仓库目录职责、启动方式、测试方式、关键接口、编码约束、中文化要求与常见修改入口
- **则** 可以据此独立完成常规开发与验证工作

## 调整要求
### 要求：仓库运行与交付方式
系统 SHALL 以 “基于 `.NET 10` 的 C# 后端 + Next.js 前端” 作为默认开发、测试、部署与文档说明的唯一官方技术栈组合。

#### 场景：新开发者按文档启动项目
- **当** 新开发者按照仓库文档进行环境准备与启动
- **则** 使用 `.NET 10` 工具链启动后端
- **则** 使用 Node.js 工具链启动前端
- **则** 无需依赖 Python/Poetry 即可完成标准开发流程

### 要求：C# 运行时版本固定
系统 SHALL 将 C# 后端的目标运行时、SDK、容器基础镜像与 CI 校验版本统一固定为 `.NET 10`，不得在实现阶段使用其他 .NET 主版本替代。

#### 场景：开发与交付环境保持一致
- **当** 开发者在本地、CI 或容器环境中构建和运行 C# 后端
- **则** 使用的 SDK 与运行时版本均指向 `.NET 10`
- **则** 项目文件、镜像、脚本与文档中的版本声明保持一致
- **则** 不会因 .NET 主版本不一致导致构建或运行偏差

### 要求：仓库主目录边界
系统 SHALL 将仓库主目录约束为仅保留 C# 后端、Next.js 前端与必要的仓库级配置；被淘汰或过渡中的 Python 逻辑不得继续散落在主目录中。

#### 场景：迁移完成后检查主目录
- **当** 维护者检查仓库主目录结构
- **则** 主目录中的业务实现仅包含 C# 与 Next.js 相关逻辑
- **则** 存量 Python 代码若仍需保留，仅存在于约定的独立收拢目录
- **则** 不存在新的主目录级 Python 业务模块

### 要求：国际化策略
系统 SHALL 使用中文作为默认且唯一维护语种，前端不再要求维持多语言切换能力。

#### 场景：用户浏览界面
- **当** 用户打开前端页面
- **则** 页面展示中文文案
- **则** 不再出现面向最终用户的多语种切换入口

## 移除要求
### 要求：Python 后端作为官方运行时
**原因**：目标技术栈已统一为 C# 后端，继续维护 Python 后端会增加双栈成本。  
**迁移策略**：先将 Python 代码收拢到独立子目录，再将现有能力映射到 C# 服务；在迁移完成并验证后移除 Python 依赖、入口与测试。

### 要求：多语种 README 与前端翻译资源
**原因**：当前需求明确要求只保留中文内容，以减少文档分叉和维护负担。  
**迁移策略**：合并内容到中文 README 与中文界面文案，删除其他语种文档与翻译资源，并更新引用关系。
