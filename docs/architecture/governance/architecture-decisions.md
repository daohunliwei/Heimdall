## 文档范围

本文汇总当前仍然有效的关键架构决策，用来回答“为什么系统会长成现在这样”。每条决策都关注背景、选择、影响范围和后续约束，作为后续 ADR/AD 的统一沉淀位置。

## 核心职责

| 职责主题 | 具体职责 | 产出或约束 |
|------|------|------|
| 决策归档 | 统一沉淀长期有效的架构原则与关键选择 | AD 清单、决策摘要、影响范围说明 |
| 边界约束 | 为新增接口、实体、任务链路和 Provider 扩展提供边界判断依据 | 研发实现前的架构校验基线 |
| 变更评审 | 为后续 ADR/AD 增补、旧决策更新和历史方案退场提供对照面 | 决策是否仍然有效、是否需要新增记录 |
| 跨专题对齐 | 约束入口页、路线图和运行时专题中的原则性表述 | 保证关键架构事实只有一个主要落点 |

## 关键结构

### 决策清单

| 编号 | 决策主题 | 影响范围 |
|------|------|------|
| AD1 | `RepositoryVersion` 与 `WikiVersion` 分离 | 全部运行时读写路径 |
| AD2 | PostgreSQL 为唯一信源 | 持久化、恢复、导出 |
| AD3 | BM25 + pgvector 混合检索 | Wiki 生成、问答、检索效果 |

| AD5 | 长任务统一后台队列 | Wiki、Ask、Slides、Workshop |
| AD6 | 阶段工件支持断点续跑 | 长任务恢复与审计 |
| AD7 | SqlSugar CodeFirst 自动同步 | 实体演进、数据库管理 |
| AD8 | MEAI `IChatClient` 统一模型调用 | Provider 接入、流式输出、可观测性 |
| AD9 | `repositoryId` 为统一主标识 | 前后端路由与 API 契约 |

### 决策记录骨架

| 组成部分 | 说明 | 使用目的 |
|------|------|------|
| 决策编号 | 使用 `ADx` 递增编号标识长期有效原则 | 便于被路线图、专题页和实现说明引用 |
| 决策主题 | 用一句话概括“做了什么选择” | 让读者快速定位关注点 |
| 选择原因 | 说明为什么不是其他方案 | 保留背景，避免重复讨论旧结论 |
| 影响范围 | 标明会影响哪些模块、接口或治理动作 | 帮助开发者评估变更半径 |
| 后续约束 | 说明新增实现时必须遵守的边界 | 将决策从“文档知识”转为“工程约束” |

### 当前有效决策摘要

### AD1：双版本分离

- **选择**：代码快照和知识版本分离建模。
- **原因**：允许同一代码版本多次生成，支持发布、回滚和差异比较。
- **影响**：所有接口和任务都必须显式传递版本上下文。

### AD2：数据库唯一信源

- **选择**：正式数据统一落 PostgreSQL，文件系统仅作临时暂存。
- **原因**：降低双写不一致风险，提升恢复与审计能力。
- **影响**：导出、问答、派生内容都以数据库中的版本数据为准。

### AD3：混合检索

- **选择**：BM25 与 pgvector 双路召回后再做 RRF 融合。
- **原因**：同时兼顾符号精确命中和语义相似度检索。
- **影响**：需要同时维护内存索引和向量检索链路。

### AD4：Markdown 优先

- **选择**：Markdown + Frontmatter + Mermaid 为主内容格式。
- **原因**：便于版本比较、渲染、导出与跨场景复用。
- **影响**：Slides/Workshop 更适合基于稳定结构工件生成，而不是直接输出 HTML。

### AD5：长任务队列化

- **选择**：统一由 `TaskQueueService` 与后台 Worker 执行长任务。
- **原因**：便于排队、恢复、审计与并发控制。
- **影响**：控制器只返回 `task_id`，结果通过状态接口或 SSE 获取。

### AD6：阶段工件恢复

- **选择**：每个阶段完成后落库工件，并记录最近成功阶段。
- **原因**：避免大任务失败后从头开始。
- **影响**：任务表和工件表成为恢复链路的核心依赖。

### AD7：SqlSugar CodeFirst

- **选择**：使用 SqlSugar 自动同步表结构，而非迁移文件驱动。
- **原因**：降低当前迭代期的迁移维护成本。
- **影响**：实体定义必须准确表达表结构，变更前需要评估向后兼容性。

### AD8：MEAI 标准化调用

- **选择**：采用 MEAI `IChatClient` 替代自研接口。
- **原因**：复用标准生态、中间件与真流式能力。
- **影响**：Provider 接入按兼容工厂或自定义适配器两条路径治理。

### AD9：统一 `repositoryId`

- **选择**：前后端统一使用 `repositoryId` 作为仓库主标识。
- **原因**：避免仓库重命名、跨 Provider 命名差异带来的不稳定性。
- **影响**：页面路由、接口设计和分享链接都围绕该标识组织。

## 关键流程

### 架构决策治理闭环

1. 当系统引入跨模块、跨版本、长期生效的结构性变化时，先判断它是否属于新的架构决策，而不是普通实现细节。
2. 若属于长期原则，则在本文新增或更新对应 `ADx` 条目，补充选择、原因、影响范围和后续约束。
3. 决策确认后，需要同步检查入口页、相关专题文档与实现说明，避免同一事实在多个文档中出现冲突表述。
4. 研发在新增接口、实体、任务阶段或 Provider 适配时，应回查本文，确认实现没有突破既有决策边界。
5. 当旧决策被新方案替代时，应在本文显式更新状态与适用范围，并由路线图记录其落地时间点。

## 设计取舍

| 取舍点 | 当前做法 | 说明 |
|------|------|------|
| 决策记录形式 | 合并为单一长期维护文档 | 适合当前仓库规模，便于新人集中查阅 |
| 决策粒度 | 只记录跨主题长期有效原则 | 避免把临时实现细节写成架构决策 |
| 表达方式 | 背景 + 选择 + 影响 | 让读者既知道做法，也知道边界和代价 |
