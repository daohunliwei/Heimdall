# Heimdall 联调问题记录

## 问题 1：路由冲突 — `GET /tasks/{id}/status`

**严重程度**: 高（功能不可用）

**现象**: 调用 `GET /tasks/{id}/status` 返回 `AmbiguousMatchException`。

**原因**: `TasksController` 和 `TaskStatusController` 都使用 `[Route("tasks")]` 且都定义了 `[HttpGet("{id}/status")]`。

**修复**: 删除 `TasksController.GetTaskStatus()` 桩方法。

**状态**: ✅ 已修复 — `TasksController.cs`

---

## 问题 2：DI 注册缺失 — `TaskLlmCallLogService`

**严重程度**: 高（功能不可用）

**现象**: `GET /tasks/{id}/llm-calls` 返回 500：`Unable to resolve service for type 'TaskLlmCallLogService'`

**原因**: 类存在但未在 DI 容器注册。

**修复**: 在 `Program.cs` 添加 `builder.Services.AddScoped<TaskLlmCallLogService>()`。

**状态**: ✅ 已修复 — `Program.cs`

---

## 问题 3：Dashboard 统计值硬编码 — `total_wikis = 0`

**严重程度**: 中（数据展示错误）

**现象**: Dashboard 返回 `total_wikis: 0`，即使 Wiki 已生成。

**原因**: `DashboardService.GetDashboardStatsAsync()` 中 `TotalWikis = 0` 硬编码。

**修复**: `IWikiRepository` 添加 `GetAllAsync()` / `CountAsync()` → `WikiRepository` 实现 → `DashboardService` 改为 `await _wikiRepo.CountAsync()`。

**状态**: ✅ 已修复 — `IWikiRepository.cs`, `WikiRepository.cs`, `DashboardService.cs`

---

## 问题 4：GitLab 仓库 Owner 解析错误

**严重程度**: 高（数据正确性）

**现象**: URL `http://gitlab.beisencorp.com/AppCenter/Beisen.AppCenter.Ops` 解析后 owner=repo=`Beisen.AppCenter.Ops`。

**原因**: `WikiTaskService.ExtractRepoName()` 只取 URL 最后一节。未使用已有的 `IRepositorySource.ParseOwnerRepo()`。

**修复**:
1. `WikiTaskService` 注入 `RepositoryAccessService`
2. `RepositoryAccessService.FindSource()` 改为 public
3. 所有 `ExtractRepoName()` 调用替换为 `_repoAccess.FindSource(...).ParseOwnerRepo(...)`
4. 删除 `ExtractRepoName` 死代码

**状态**: ✅ 已修复 — `WikiTaskService.cs`, `RepositoryAccessService.cs`

## 问题 5：WikiPage 外键违规 — WikiId 为 Guid.Empty

**严重程度**: 致命（数据无法入库）

**现象**: `23503: insert or update on table "wiki_pages" violates foreign key constraint "FK_wiki_pages_wikis_WikiId"`

**原因**: `SaveWikiPageAsync()` 在页面生成时立即保存，但此时 Wiki 记录尚未创建（`SaveWikiAsync` 才创建 Wiki）。

**修复**:
1. 页面生成循环**前**先创建 Wiki 记录
2. `SaveWikiPageAsync` 接受 `wikiId` 参数
3. `SaveWikiAsync` 简化为仅更新 Wiki 元数据

**状态**: ✅ 已修复 — `WikiTaskService.cs`

## 问题 6：LLM XML 解析失败导致仅生成 1 页

**严重程度**: 高（影响生成质量）

**现象**: `gemma4:e2b` 生成的结构 XML 存在标签错配（`<page_ref>page-6</page-6>` 等），解析失败后回退到硬编码单页兜底。

**原因**: 小模型（5B）XML 输出质量不稳定。原有 `RepairXmlIssues` 仅处理 `parent_section`/`section` 错配。

**修复（三层防线）**:
1. **RepairXmlIssues** 增强 — 新增 `page_ref`/`section_ref`/`related` 标签错配修复
2. **ParseWikiStructureWithRegex** (新增) — XML 解析失败时用正则直接提取 page/section 结构，容忍标签不匹配
3. **BuildFallbackStructure** — 仅在前两种都失败时使用

**状态**: ✅ 已修复 — `WikiTaskService.cs`

## 问题 7：LLM Call Log 中 token 统计硬编码

**严重程度**: 低（展示不完整）

**现象**: `TokenSummaryResponse.CallCount` 始终为 0，`TotalCost` 始终为 0。

**原因**: `TaskLlmCallLogService.GetTokenSummaryAsync()` 中 `CallCount = 0` 和 `TotalCost = 0` 硬编码。

**修复**: 从实际日志计数 `CallCount`；Ollama 成本为 0，其他 Provider 按 $0.002/1K tokens 估算。

**状态**: ✅ 已修复 — `TaskLlmCallLogService.cs`

## 问题 8：数据库字段截断

**严重程度**: 中（调试数据不完整）

**现象**: `task_llm_call_logs` 的 `RequestPreview` 和 `ResponsePreview` 被截断为 500 字符；Wiki fallback Description 被截断为 300 字符。

**原因**: `LogLlmCallAsync` 中 `prompt[..500]` 和 `response[..500]` 硬编码截断。

**修复**:
1. `RequestPreview` / `ResponsePreview` → 存储完整内容（列类型为 `text` 无限制）
2. `BuildFallbackStructure` Description → 存储完整 LLM 响应

**状态**: ✅ 已修复 — `WikiTaskService.cs`
