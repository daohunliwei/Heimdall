## Context

当前 Heimdall 项目的开发调试依赖人工步骤：手动准备测试仓库、手动设置环境变量、手动调用 API 验证结果。Claude Code 等 AI 辅助工具在缺少标准化脚本和安全密钥管理的情况下难以高效介入。Wiki 生成任务（10 阶段管线，单次耗时可达数十分钟）一旦中断必须重新开始。全局设置页面（`/admin/settings`）使用基础 HTML 表格呈现 Provider 元数据，缺少可视化层次和环境变量管理能力。

本次设计聚焦三个维度：(1) 建立可复用的调试工作流脚本体系与文档；(2) 为 Wiki 生成管线增加调试模式和断点续跑能力；(3) 重构全局设置页面为现代化卡片式管理界面。

技术约束：后端 .NET 10 + ASP.NET Core，前端 Next.js 16 App Router，数据库 PostgreSQL + pgvector，无 Python 运行时。

## Goals / Non-Goals

**Goals:**
- 提供标准化的开发环境准备、密钥注入、服务启停、数据重置脚本，让调试流程可被任何工具（包括 Claude Code）驱动
- 建立 `.env.example` 模板 + 安全注入机制，密钥文件不入 Git，消除泄露风险
- 完善 README 文档，覆盖环境准备、Provider 配置、调试指南和常见故障排查
- 拆分 CLAUDE.md（Claude Code 专用指令）与 AGENTS.md（通用 Agent 指令），确保 Claude Code 正确识别
- Debug Mode 开关可限制 Wiki 生成最大页数，支持运行时切换，加速调试迭代
- 任务中断后支持自动恢复（服务启动时）和手动恢复（UI 按钮），从最后检查点继续
- 全局设置页面以卡片式布局展示 Provider/模型详情（连接状态、能力标签、关键参数可视化）
- 系统配置与环境变量状态页面展示当前运行时配置，敏感值掩码显示

**Non-Goals:**
- 不实现跨进程的分布式任务恢复（任务仅在单实例内恢复）
- 不实现环境变量的在线编辑写入（仅展示状态，修改通过配置文件或脚本完成）
- 不修改 Wiki 生成管线的核心业务逻辑（Debug Mode 仅截断页面列表，不改生成算法）
- 不引入第三方 UI 组件库（继续使用项目现有 CSS 变量体系）

## Decisions

### 1. 调试脚本选型：PowerShell + .env 模板

**选择**：使用 PowerShell 脚本（`.ps1`）统一管理调试流程，同时提供 `.env.example` 模板文件供密钥注入。

**理由**：项目开发环境为 Windows，PowerShell 是原生 Shell；`.env` 格式被 dotnet 和前端工具链共同支持。相比 Bash 脚本需要 WSL/Git Bash 额外依赖，PowerShell 零依赖即可运行。

**备选方案**：使用 `dotnet` CLI 自定义工具扩展——虽然更跨平台，但开发成本高，不适合快速迭代期的调试脚本。

### 2. Debug Mode 配置存储：数据库系统设置表

**选择**：在 `AppDbContext` 中增加 `SystemSettings` 表（或扩展现有配置机制），以 key-value 存储 Debug Mode 开关和页数上限。

**理由**：支持运行时热切换，无需重启服务；与现有 `provider_model_metadata` 表的运行时更新模式一致。页数限制默认 5 页，可通过 API 调整。

**备选方案**：环境变量控制——虽然简单但无法运行时切换，每次改完需要重启服务，与"快速调试迭代"目标矛盾。

### 3. 任务断点续跑：基于现有检查点工件

**选择**：复用 `task-progress-persistence` spec 中已定义的阶段落盘和批次工件持久化机制，新增 `POST /api/tasks/{id}/resume` 端点和 `TaskResumeService` 启动扫描逻辑。

**恢复策略**：
- 自动恢复：`TaskResumeService` 作为 `IHostedService` 在启动时扫描 `Running` 状态的任务，从最后完成的阶段/批次继续执行
- 手动恢复：前端任务列表展示"可恢复"标记和恢复按钮，调用 Resume API
- 恢复粒度：阶段级（Stage）和批次级（Batch），取两者中更精细的进度点

**理由**：底层检查点机制已就绪，只需增加调度层逻辑。避免重新设计检查点存储。

**备选方案**：使用 Hangfire/Quartz 等任务调度框架管理恢复——引入新依赖，对当前需求过度设计。

### 4. 全局设置页面：卡片式布局 + 分组可视化

**选择**：以 Provider 为单位使用卡片组件，每张卡片顶部显示 Provider 名称和连接状态指示灯，内部以标签组展示模型能力（上下文窗口、最大输出、计费类型），底部提供编辑/删除操作。系统配置区域以分组折叠面板展示运行时配置和环境变量状态。

**组件拆分**：
- `ProviderCard` — 单个 Provider 及其模型列表的卡片
- `ModelTagGroup` — 模型能力参数的可视化标签组
- `ConfigStatusPanel` — 系统配置项键值对展示面板
- `EnvVarStatusPanel` — 环境变量状态面板（已设置/未设置/默认值，敏感值掩码）

**理由**：表格视图适合密集数据编辑，但不利于快速浏览 Provider 整体状况。卡片视图提供更好的信息层次，连接状态指示灯让问题一目了然。

**备选方案**：使用 TDesign/Ant Design 等组件库——引入重量级依赖，与项目轻量化的 CSS 变量体系风格冲突。

### 5. CLAUDE.md 与 AGENTS.md 分离策略

**选择**：CLAUDE.md 仅包含 Claude Code 专用指令（工具使用提示、项目特定约定），通过文件头 `# CLAUDE.md` 标识；AGENTS.md 保留通用 Agent 行为指令（代码规范、架构约束、修改原则）。

**理由**：用户反馈 CLAUDE.md 引用 AGENTS.md 的方式导致 Claude Code 无法正确识别指令。直接拆分可解决此问题，后续如需合并再用工具链生成聚合文件。

## Risks / Trade-offs

- **[风险] 调试脚本仅覆盖 Windows/PowerShell** → 后续可补充 Bash 版本脚本或使用跨平台 `dotnet` 工具
- **[风险] 自动恢复可能恢复一个因逻辑错误而反复失败的任务** → 设置最大自动重试次数（3 次），超过后标记为 `Failed` 并记录失败原因，需人工介入
- **[风险] Debug Mode 截断页面可能导致生成结果不完整，误判为管线 Bug** → 在 Debug Mode 输出的页面中显示明显的"调试模式截断"标记
- **[风险] 环境变量状态展示可能泄露密钥前缀** → 敏感值以 `***ABC123` 格式掩码（仅显示最后 6 字符），完全未设置的显示"—"
- **[取舍] 任务恢复粒度受限于检查点密度** → 当前检查点在阶段和批次边界，恢复后最多重复执行当前批次，不会重复已完成批次

## Open Questions

- 是否需要支持"指定恢复点"（从某个特定阶段/批次重新开始），而不是仅从最后检查点恢复？当前设计为"仅从最后检查点恢复"，如需指定恢复点可后续扩展
- 系统配置在线编辑是否需要 Admin 权限二次确认？当前设计仅展示不编辑，后续可扩展编辑能力
